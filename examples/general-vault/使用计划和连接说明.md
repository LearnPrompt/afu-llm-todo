# Afu 使用计划和连接说明

这份使用说明只针对当前安全演示 Vault：

```text
/Users/yichenlin/Desktop/Work/afu-llm-todo/examples/general-vault
```

不要直接拿真实 `All About Me` Vault 做第一轮演练。这个演示 Vault 的任务是把 Afu 的能力尽量完整地跑一遍：收件箱扫描、转卡、去重、排期、写回 Markdown、Wiki Mode、每日提醒、归档、外部日历连接和安全边界。

## 三、网页 UI 演练

### 1. 工作区设置

打开页面后先看“工作区设置”。

应该看到：
- Vault 根目录指向 `general-vault`。
- 收件箱目录是 `00_收件箱`。
- 选题/行动卡目录是 `40_行动卡片`。
- 同步目标是“只写 Markdown”。

操作：
- 保存一次目录设置。
- 刷新页面。
- 确认设置没有丢。

### 2. 收件箱扫描

进入“收件箱”页签。

应该看到：
- 20 条演示素材里，已经被旧卡片引用的 02、03、04 可能不会再出现在候选里。
- 新增的 11-20 应该能作为候选出现。
- 每条卡片应该显示标题、摘要、标签和置信度提示。

操作：
- 搜索 `weekly`、`privacy`、`portfolio`、`health`。
- 改每页数量。
- 翻页。
- 本页全选。

### 3. 单条转卡

建议先测这几条：
- 11 运动和恢复：验证 daily task。
- 12 深度工作：验证工作任务。
- 18 财务账单：验证隐私边界。
- 20 作品集发布：验证项目交付任务。

操作：
- 点单条“转卡”。
- 看是否自动进入排期池。
- 看是否自动弹出排期窗口。
- 回到 `40_行动卡片/` 检查生成的 Markdown。

重点观察：
- 当前版本模板仍然偏“选题策划”，如果它把运动、财务也生成“可拍主张”，说明产品模型还没升级成功。
- `source_inbox_path` 是否写对。
- 操作日志是否写入 `99_系统/topic-planner-log/`。
- 如果想让已转卡素材重新回到候选里，用卡片上的“撤回转卡”。它会删除生成的行动卡，但保留原始收件箱素材。

### 4. 批量转卡

建议选：
- 12 深度工作
- 13 作业截止
- 15 家务补给
- 16 每周复盘

操作：
- 本页多选。
- 批量转卡。
- 看是否逐张进入排期队列。
- 观察合并、失败和成功提示。

重点观察：
- 批量中某一条失败时，其他条是否继续。
- 生成的卡是否重复。
- 队列弹窗顺序是否符合操作预期。

### 5. 排期和周历

操作：
- 给一张卡排到今天上午整理 `09:30-10:30`。
- 给第二张卡排到同一天同一时间，观察冲突提示。
- 给一天排超过 3 张，观察每日容量提示。
- 拖拽卡片到另一天。
- 重新排期。
- 取消排期。

重点观察：
- Markdown frontmatter 是否更新 `scheduled_date`、`scheduled_start`、`scheduled_end`。
- 周历是否实时刷新。
- 冲突和容量只是提醒，不是硬限制。

### 6. 拒绝和归档

建议用演示卡，不要用你想保留的卡。

操作：
- 拒绝一张卡，填写原因。
- 确认它从排期池和周历隐藏。
- 归档一张卡，确认文件移动到归档目录。

重点观察：
- 当前代码已知归档源文件处理不完整，源素材可能重新出现在候选里。
- 拒绝应该保留卡片文件，只改状态。

## 四、每日提醒演练

每日提醒不是后台定时任务，它靠 URL 参数打开弹窗。

打开：

```text
http://localhost:4317/?dailyInbox=1&inboxDate=2026-06-26
```

操作：
- 看弹窗是否只列出 `00_收件箱/2026-06-26/` 里的候选。
- 全选当天。
- 取消确认。
- 再选 2-3 条导入。

重点观察：
- 它不能把历史 backlog 误报成今日新增。
- 没有候选时要明确显示当天无可处理项。

## 五、Wiki Mode 演练

网页里没有 Wiki 操作入口，但后端 API 存在。

可以演练的链路：

```text
Inbox candidates -> Wiki ingest packet -> Todo candidates -> Accept Todo -> Card
```

API：
- `POST /api/wiki/compile`
- `POST /api/wiki/todos/generate`
- `POST /api/wiki/todos/accept`
- `POST /api/wiki/todos/reject`

预期：
- `30_整理Wiki/` 里生成 packet 或候选记录。
- 接受 Todo 后进入 `40_行动卡片/`。
- 拒绝 Todo 只写日志，不删除来源素材。

重要限制：
- 当前 Wiki Mode 不会真正自动维护知识图谱。
- 它生成的是给外部 Agent 使用的 Markdown packet。
- 真正的整理和判断仍然需要 Agent 或人继续处理。

## 六、外部日历连接演练

当前演示 Vault 默认 `calendarProvider: none`，第一轮建议保持这样。

### Markdown-only

适合第一轮。

预期：
- 只更新卡片 Markdown。
- 不触发飞书或 macOS Calendar。

### 飞书

需要本机安装并配置 `lark-cli`。

页面会检查：
- 是否找到 `lark-cli`。
- 是否已经初始化应用配置。
- 是否有用户日历授权。
- 是否能访问主日历。

注意：
- 当前代码同步到飞书主日历，不是专用演示日历。
- 演练前最好用演示账号。
- 当前版本有时区风险，不建议直接接真实工作日历。

### macOS Calendar

需要系统授权 Calendar。

注意：
- 最好先建一个专用演示日历。
- 不要留空日历名直接写默认日历。
- 当前代码在日历名找不到时有写错目标的风险。

## 八、完整使用路线

建议分 6 轮。

### 第 1 轮：只读扫描

- 启动网页。
- 确认设置。
- 查看收件箱候选。
- 不转卡。

通过标准：
- 能读到演示 Vault。
- 候选数量和已引用排除逻辑合理。

### 第 2 轮：Markdown-only 转卡

- 单条转卡。
- 批量转卡。
- 检查 `40_行动卡片/`。
- 检查日志。

通过标准：
- 卡片创建成功。
- 来源路径正确。
- 不碰外部日历。

### 第 3 轮：排期

- 排 3 张不同类型卡。
- 测冲突。
- 测每日容量。
- 测取消排期。

通过标准：
- frontmatter 更新正确。
- UI 刷新正确。

### 第 4 轮：生命周期

- 拒绝。
- 归档。
- 重新扫描候选。

通过标准：
- 拒绝卡隐藏但文件保留。
- 归档卡移动到归档目录。
- 已知问题要记录：源素材可能重新出现。

### 第 5 轮：Wiki Mode / Agent

- 生成 Wiki packet。
- 生成 Todo candidates。
- 接受一条 Todo。
- 拒绝一条 Todo。

通过标准：
- Wiki 目录有记录。
- 接受后创建卡片。
- 拒绝后只写日志。

### 第 6 轮：外部日历

只在前 5 轮稳定后演练。

- 先验证 macOS 专用演示日历。
- 再测飞书演示账号。
- 不要直接测真实主日历。

## 九、当前最重要的产品判断

这个演示 Vault 现在故意加入了很多非内容选题任务：运动、家务、财务、关系、作业、deep work、作品集。

如果 Afu 仍然把这些都生成：

```text
type: 选题策划
target_forms: 视频
可拍主张
开头钩子
主体结构
```

那说明当前产品模型还停留在“内容选题规划器”，没有升级成“通用个人行动系统”。

后续真正要做好的方向是：
- 根据 `task_domain` 和 `expected_card_type` 生成不同模板。
- 对 `privacy: private` 默认只生成内部复盘卡。
- 对 `recurrence: daily/weekly/monthly` 生成不同排期建议。
- 对大规划素材支持拆成多张卡。
- 对生活、工作、学习、求职使用不同完成标准。

这就是这 20 条演示素材的意义：它不是为了好看，是为了逼出当前模型到底能不能处理真实人生里的混合任务。
